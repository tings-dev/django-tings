# Reusable Datastar tables for Django

Status: ready-for-agent

## Problem Statement

Carbonsheet lets users search a table as they type, share filtered views, and review dense records on desktop or mobile. Another Django project that wants this behavior currently has to take along Carbonsheet’s templates, browser code, styles, and assumptions about permissions and data. Maintaining a second copy would mean fixing the same interactions in two places.

## Solution

Create the MIT-licensed `django-tings` library from the frkl-dev Python project template. Its first helper, `django_tings.interactive_table`, gives a Django view a server-rendered django-tables2 table with Datastar live updates. A project can start with columns, a caption, and a loader for its records. It can then configure a richer table or apply its own theme.

Replace Carbonsheet’s shared table implementation with this library in the dedicated integration worktree. Completion means that a minimal Django project and Carbonsheet both run the same installed wheel and pass the acceptance checks below.

## User Stories

1. As a Django developer, I want to install one package and render a table with the usual django-tables2 template tag, so that I can add a searchable directory to an existing page.
2. As a Django developer, I want usable templates, styles and scripts in the wheel, so that I can use the table without adopting Carbonsheet’s frontend build.
3. As a view author, I want to pass a loader scoped to the current request, so that rows, filter choices and counts respect the user’s access on every refresh.
4. As a view author, I want the same loader contract for database queries, in-memory records and staged imports, so that I can choose the appropriate data source for each view.
5. As an import developer, I want to supply columns discovered for one import session, so that a preview can display the fields actually present.
6. As a directory user, I want results to update when I pause typing, so that I can refine a search while keeping my place in the search field.
7. As a directory user, I want a new search to start on page one and retain my sort and column filters, so that searching from a later page gives me meaningful results.
8. As a table user, I want to sort, page, and narrow results using choices, date ranges or quick-filter chips, so that I can find records without scanning the whole dataset.
9. As an import reviewer, I want chip counts for the authorized import alongside the count of current matches, so that I can see how much work remains while examining a subset.
10. As a dashboard user, I want several table instances to keep independent searches and pages, so that working in one preserves the others and my active tab.
11. As a table user, I want to bookmark a view and use Back and Forward, so that I can return to the records I was reviewing.
12. As a user on a slow connection, I want the latest search to win and failed searches to be retryable, so that I can trust the rows on screen and keep what I typed.
13. As a user with JavaScript disabled, I want an ordinary search form and working sort and page links, so that I can reach the same records through full-page navigation.
14. As a keyboard or screen-reader user, I want labeled controls, stable focus and an announcement when results change, so that I can keep working after a refresh.
15. As a mobile reviewer, I want the important fields on each record card and the remaining fields in its details, so that I can identify and act on a record on a narrow screen.
16. As a reviewer of wide tables, I want sticky headers, units in headings and an optional pinned identity column, so that values stay interpretable while I compare them.
17. As an import reviewer, I want labeled statuses, changed cells and previous values, so that I can understand a proposed change without relying on color.
18. As a reviewer, I want to select eligible records across pages and submit them together, so that filtering or paging does not discard my work.
19. As a table user, I want row and cell links, return navigation, and explanations for disabled actions, so that I can act on a record and return to the same view.
20. As a user viewing an empty table, I want to know whether the dataset is empty or my filters found no matches, so that I can choose the next available action.
21. As a project designer, I want to customize spacing, colors and individual components, so that desktop, mobile and refreshed tables fit the host application.
22. As a German-speaking user, I want table controls, counts and feedback in my chosen language, so that the table reads consistently with the surrounding page.
23. As a Carbonsheet maintainer, I want every existing table to use the packaged implementation, so that fixes to shared behavior have one home while business rules stay in Carbonsheet.

## Implementation Decisions

- **Distribution.** Use the requested Copier template. Give each ting its own import path. The interactive table warrants a Django app package for its Python modules, template tags, templates, static assets and compiled catalogs. First-release targets are Python 3.12+ and Django 6.0.x and 6.1.x. The maintainer authorized adapting Carbonsheet’s first-party table code under MIT. Include upstream licenses for bundled third-party assets.
- **Public data interface.** Declare columns on an `InteractiveTable` using django-tables2. The approved prototype call is `await ContactsTable.for_request(request, load_page=load_page)`. The view supplies an async loader for the authorized dataset. It receives a normalized `TableQuery` and returns `TablePage(rows, total)`, optionally with choices and facet counts. The total counts matches before pagination. Given that total, `query.page_slice(total)` supplies the clamped slice, so an out-of-range request returns the rows for the effective page. The instance can receive extra columns, column exclusions and fixed endpoint parameters. The host owns projections, route resolution and authorization on initial GET, refresh and action submission.
- **Query and live search.** The server interprets the same explicit parameters on ordinary GET and Datastar refresh. A single table can use `q`, `page`, `sort`, `direction` and declared `filter_*` fields, including range bounds. Accept only declared sort and filter fields and normalize invalid page values. After a 300 ms pause in typing, refresh results, total and pager in place, reset the page to one, retain sort and column filters, and preserve focus and caret. Clearing search text keeps other active filters. The Clear filters action clears search and column filters and retains the sort.
- **Instance ownership.** For multiple tables sharing a URL, the view assigns each a stable instance name. For example, `?clients-q=steel&suppliers-page=4&tab=review` describes two tables and their containing page. A successful interaction updates that instance’s parameters in the current URL. Links and GET forms preserve sibling state and host context, including fixed parameters and return links. Scope signals, patch targets, focus, selection, pending requests, busy indicators and errors to the instance. This applies to multiple copies of one table definition and to independently navigable tables in tab panels.
- **History and refresh ordering.** A successful live search replaces the current history entry. Successful page, sort, chip and Clear clicks add an entry. Back and Forward restore the view described by the URL and respect host-owned transitions such as a details sheet. Commit rows and their effective URL together. A superseded response cannot change rows, counts, focus, busy state or history. A failed refresh keeps the last successful rows and URL, preserves the input for retry, and reports an actionable error on that table.
- **Presentation interface.** Supply a standalone default and an optional `TableDisplay` on the class, with per-instance overrides for request-specific values. Use documented, scoped `--it-*` CSS properties for visual styling. A project-wide theme or instance-level `theme=` can name Django templates for components such as badges, empty content and action content. Document the context those templates receive and use it on initial render, mobile cards and SSE patches. The library owns interactive wrappers, keyboard behavior, live regions and patch targets. Normal django-tables2 custom columns remain available.
- **Controls and layout.** Preserve visible, collapsed and hidden search modes, sortable fields and default order, select and date-range filters, multi-value chips and defaults, page size, and pager placement and alignment above or below. Support compact and comfortable density, static height with placeholder rows, truncation, sticky headers, optional wide layout, comparison scrolling and pinned identity. Configure column kinds, sublabels and units, mobile heading, summary, badge and details. Preserve a readable narrow-screen fallback when cards are unconfigured.
- **Review and actions.** Support translated status labels, tones and icons, per-row and per-cell tones, and cell differences with previous values. Keep accessible names for icon-only desktop status and full labels on cards. Expose row and cell targets, same-page details, return links, disabled reasons, and missing-value behavior. Preserve per-instance selection across in-place pagination and filtering. Bulk actions POST eligible record keys and extra fields with CSRF protection. The application checks the submitted records and authorizes the action. Empty and filtered-empty states can offer a permitted action.
- **Assets and localization.** A namespaced assets include supplies the default CSS, browser enhancement and a locally served Datastar runtime. Include these once on pages hosting tables and allow the host to supply its existing runtime. Generic labels, messages and plurals use Django localization, with translated strings supplied to JavaScript. Ship the compiled German catalog. The host supplies business vocabulary, branded styles and fonts.
- **Carbonsheet cutover.** Work in the existing integration worktree. Baseline the current callers and tests, then migrate one searchable directory end to end. Follow with scoped detail factories, import review, in-memory workspaces and historical auctions. Move the initial views, controls and refresh endpoints together. Preserve existing links, safe return paths, permission and tenant checks, and host-owned actions. Audit consumers of `tableKey`, configuration signals and signal-only searches. Validate table selection on the server. Keep a Carbonsheet compatibility adapter only for an identified remaining caller, and track temporary import aliases to their callers. Remove the superseded shared implementation once all production callers resolve to the library.

## Testing Decisions

**Test boundary.** Exercise the installed library through the host’s public Django views, real GET forms and links, and Datastar refreshes. The standalone app and Carbonsheet are two consumers of this same interface. Assert which records, controls, URLs and feedback a user receives and what actions the host permits. Use existing request, template and browser tests for focused regression coverage.

1. **Prove the artifact.** Build one wheel, record its version and checksum, and install that wheel non-editably in both a clean minimal project outside the source checkout and the Carbonsheet worktree. Verify imports, template and tag discovery, collected static assets, licenses, and German strings and plurals. Exercise both packaged and host-supplied Datastar, with one runtime per page.
2. **Prove the supported combinations.** Run the standalone checks on Python 3.12, Django 6.0 and the minimum supported dependencies, including the django-tables2 2.x line. Also run on Carbonsheet’s locked stack. At the migration baseline that is Python 3.14+, Django 6.1.1, django-tables2 3.0.1 and datastar-py 1.0.3. Record the exact versions tested.
3. **Run the defining live-search scenario in both consumers.** Start on page two with a sort and column filter applied. Type a search and pause for the debounce. Verify the loader receives the term, page one appears without pressing Enter or reloading, and the rows, count and pager agree. Check focus, caret, sort and filter retention. Reopen the resulting URL and compare rows. Deliver an older response after the newer one, then exercise failure, retry and clear. With JavaScript disabled, submit the same search form and compare the result.
4. **Exercise independent instances.** Mount two named copies of the same table in the standalone app. Search one while the other stays on a later page. Interleave their refreshes and check the URL after each completion. Test reload, Back and Forward, including the active host tab. An error or selection in one instance must leave its sibling usable.
5. **Cover every Carbonsheet entry point.** Inventory initial GET and refresh routes and exercise every one, including historical auctions. Check correct table selection, fixed route context, and authorization for rows, choices, counts and actions. Verify a filter-only URL, an explicit clear, clamped pagination and any remaining signal-only caller. Trace the actual imports, rendered templates and loaded assets to the installed wheel before removing duplicate code.
6. **Exercise four real-browser workflows in Carbonsheet.** Use a directory for live search, a scoped detail page for permissions and Back/Forward, import review for dynamic columns, counts, cross-page selection and actions, and a workspace directory for in-memory rows and same-page refresh. Cover keyboard focus, accessible status feedback, empty/error/disabled states, translated or expanded copy, reduced motion, sticky headers and mobile details. Use the project browser helper at 360, 768 and 1440 px, including 200% zoom and 30% copy expansion.
7. **Use the existing regression suites.** Carbonsheet already exercises query normalization, sorting, rendering, SSE success and error handling, authorization, import facets and browser DOM behavior. Keep these behavioral assertions when source locations change. Run the focused suites, full Carbonsheet tests, project checks, German catalog verification and compilation, and the sticky-header and ephemeral-toolbar Node checks where separately invoked. Record baseline failures, commands, versions, routes exercised and unresolved regressions at sign-off.

## Out of Scope

Additional tings, unrelated Carbonsheet UI redesign, and changes to domain models or business policies belong to separate efforts. Production deployment and public package publication are outside the validation contract. Sign-off uses the locally built wheel.
